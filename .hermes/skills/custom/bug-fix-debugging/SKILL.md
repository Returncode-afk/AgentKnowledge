# Bug 修复与调试方法论

## 核心原则

1. **先定位，后修复** - 找到根本原因再动手
2. **验证复现** - 确认 bug 存在，了解复现条件
3. **考虑联动** - 修改一处时思考对其他功能的影响
4. **测试闭环** - 修复后必须验证

---

## 一、编写功能前的联动思维

### 核心理念

**写代码前先想联动** —— 当我们要实现一个功能时，必须在动手之前就想清楚：

1. 这个功能会影响哪些地方？
2. 哪些地方调用这个功能？
3. 哪些地方需要同步更新？
4. 哪些视图/组件需要同时修改？

### 思考框架

```
当你写一个新功能时，问自己：
    │
    ├── 这个函数/变量在哪里被调用？
    │       │
    │       └── 列出所有调用方
    │
    ├── 这个状态在哪里显示？
    │       │
    │       └── UI 组件 A？组件 B？都要改吗？
    │
    ├── 这个数据在哪里读取？
    │       │
    │       └── API？本地存储？缓存？
    │
    ├── 改动后需要重启服务吗？
    │       │
    │       └── Node.js / Python / Java 需要
    │
    ├── 有什么测试可以验证？
    │       │
    │       └── 手动测试 + 自动化测试
    │
    └── 产品流程是否受影响？
            │
            └── 查看功能流程图，确认改动对整体流程的影响
```

### 联动检查清单

写功能前必须回答：

- [ ] 我修改的函数有几个调用方？
- [ ] 我修改的 UI 组件有几个地方在用？
- [ ] 我新增的 API 有几个消费者？
- [ ] 状态变化需要同步到哪些视图？
- [ ] 修改后需要重启服务吗？
- [ ] 有没有现有测试可以运行？
- [ ] **产品功能流程图是否有标注联动点？**
- [ ] **改动是否影响标注的联动流程？**

## 二、七步调试法

### 第一步：收集信息

- 询问用户具体的错误表现
- 记录错误出现的操作步骤
- 了解预期行为 vs 实际行为
- 检查日志和错误信息

### 第二步：缩小范围

- 确定是前端问题还是后端问题
- 是 UI 问题还是数据问题
- 是单点问题还是系统性问题

### 第三步：追踪数据流

```
用户操作 → UI 事件 → API 调用 → 后端处理 → 数据库/文件 → 响应 → UI 更新
```

### 第四步：检查数据状态

- 使用 API 测试工具验证后端数据
- 检查状态文件（如 state.json、.meta.json）
- 验证文件系统的实际内容
- 检查缓存是否过期

### 第五步：定位代码

- 搜索相关函数和 API 端点
- 追踪变量赋值和传递
- 确定修复位置

### 第六步：实施修复

- 优先修复根本原因
- 注意代码联动影响
- **修改前先想联动：还有哪里在用这个函数/变量？**

### 第七步：验证修复

- 重新触发相同操作
- 确认问题已解决
- **检查是否有新问题引入**
- **测试所有联动的视图/功能**

## 三、关键检查点

### API 验证清单

```powershell
# 1. 服务是否运行
Invoke-RestMethod -Uri "http://localhost:PORT/health" -Method GET

# 2. API 响应是否正确
Invoke-RestMethod -Uri "http://localhost:PORT/api/endpoint" -Method GET

# 3. 文件系统是否同步
Get-ChildItem "项目目录/data"
```

### 常见 Bug 类型

| 类型 | 表现 | 排查方向 |
|------|------|----------|
| 数据空值 | 文件大小为 0 或返回 null | 读取路径是否正确 |
| 状态不同步 | UI 显示与实际不符 | 状态存储和读取逻辑 |
| 缓存问题 | 修改后无效 | 浏览器缓存、服务缓存 |
| 时序问题 | 间歇性失败 | 异步调用、回调顺序 |
| 联动遗漏 | 部分视图正常部分异常 | 检查所有调用方 |
| 类型错误 | undefined 或 null | 检查变量初始化 |

## 四、调试命令参考

### 文件检查

```powershell
# 文件是否存在
Test-Path "路径"

# 文件大小
Get-Item "路径" | Select-Object Length

# 文件内容
Get-Content "路径" -Head 20

# 最近修改的文件
Get-ChildItem "目录" | Where-Object {$_.LastWriteTime -gt (Get-Date).AddHours(-1)}
```

### 进程管理

```powershell
# 查找进程
Get-Process | Where-Object {$_.CommandLine -like "*关键词*"}

# 重启服务
Stop-Process -Id <PID> -Force
Start-Process -FilePath "node" -ArgumentList "app.js" -WorkingDirectory "目录"
```

## 五、联动分析模板

### 场景：修改状态显示逻辑

**问题**：某个状态在某些地方显示不正确

**联动分析步骤**：

```
1. 搜索所有设置这个状态的地方
   grep "setStatus" --include="*.js"

2. 搜索所有读取这个状态的地方
   grep "getStatus" --include="*.js"

3. 列出所有相关函数
   ├── setStatusInComponentA()
   ├── setStatusInComponentB()
   ├── getStatusFromAPI()
   └── getStatusFromLocal()

4. 确定修改范围
   └── 需要同时修改 A 和 B，只改一个会导致不一致

5. 测试所有相关功能
   ├── 测试 A 组件
   ├── 测试 B 组件
   └── 测试 A 和 B 同时操作
```

### 场景：修改共享函数

**问题**：修改了一个被多处调用的函数

**联动分析步骤**：

```
1. 找到所有调用点
   grep "myFunction" --include="*.js"

2. 理解每个调用点的上下文
   ├── 调用点 A：读取返回值 ✓
   ├── 调用点 B：读取返回值 ✓
   └── 调用点 C：不读取返回值，但依赖副作用

3. 确定修改是否破坏调用契约
   └── 如果改变了返回值格式，需要通知所有调用方

4. 逐个验证调用点
   └── 手动测试每个调用场景
```

## 六、调试心态

- **不要假设** - 实际验证每个怀疑点
- **不要猜测** - 用日志和 API 返回值说话
- **考虑联动** - 修 A 时想着 B、C 是否受影响
- **保持耐心** - 大型系统 bug 可能藏在多层调用深处
- **写前想联动** - 动手前先画联动图
- **测后想回归** - 修完一处，想哪些地方可能受影响
