# UI 功能测试清单

## 核心理念

**测试前先想联动** —— 当我们测试一个功能时，必须在动手之前就想清楚：

1. 我要测试的函数/功能被几个地方调用？
2. 哪些视图/组件共用这个状态？
3. 哪些按钮/操作会影响同一个数据？
4. 测试完一处，是否需要同步测试联动的其他地方？

---

## 测试前准备

### 1. 确认服务运行

```powershell
# 检查服务健康状态
Invoke-RestMethod -Uri "http://localhost:PORT/health" -Method GET

# 重启服务（如需要）
Get-Process | Where-Object {$_.CommandLine -like "*服务名*"} | Stop-Process -Force
Start-Process -FilePath "node" -ArgumentList "app.js" -WorkingDirectory "项目目录"
```

### 2. 确认数据状态

```powershell
# 检查数据文件
Get-ChildItem "项目目录/data" | Select-Object Name, Length

# 检查状态文件
Get-Content "项目目录/state.json"
```

### 3. 清除缓存

浏览器中按 `Ctrl+Shift+R` 强制刷新

## 联动测试策略

### 什么是联动？

**联动** = 同一个数据/状态在多个地方被读取或修改

```
示例：用户状态
    │
    ├── 显示位置 1: 导航栏 - 用户头像
    ├── 显示位置 2: 个人中心页面
    ├── 修改位置 1: 登录按钮
    └── 修改位置 2: 设置页面
```

### 联动检查框架

```
测试功能 X 之前，问自己：
    │
    ├── X 影响的数据/状态是什么？
    │
    ├── 哪些地方读取这个数据？
    │
    ├── 哪些地方修改这个数据？
    │
    ├── 需要测试的组合：
    │       ├── 视图 A 操作 → 视图 B 更新
    │       ├── 视图 B 操作 → 视图 A 更新
    │       └── 数据层修改 → 两个视图都更新
    │
    └── 产品流程是否受影响？
            │
            └── 查看功能流程图，确认测试范围是否覆盖所有联动点
```

### 搜索联动点的方法

```javascript
// 搜索状态更新函数
grep "setState" --include="*.js"
grep "updateStatus" --include="*.js"

// 搜索数据加载函数
grep "loadData" --include="*.js"
grep "fetchData" --include="*.js"

// 搜索共享变量
grep "sharedState" --include="*.js"
grep "globalState" --include="*.js"
```

## 核心测试流程

### 测试 1：状态显示一致性

**目标**: 验证状态在多个视图显示一致

**测试前联动思考**:
- 状态在几个视图显示？
- 状态在几个地方被修改？
- 每个视图都要验证！

**测试步骤**:
1. 打开应用
2. 进入视图 A，找到显示状态的组件
3. 检查状态值
4. **进入视图 B，找到显示相同状态的组件**
5. **检查状态值是否一致**

**验证点**:
- [ ] 视图 A：状态显示正确
- [ ] 视图 B：状态显示正确
- [ ] 视图 A 修改 → 视图 B 更新
- [ ] 视图 B 修改 → 视图 A 更新

### 测试 2：操作连锁反应

**目标**: 验证操作触发的连锁反应正确

**测试步骤**:
1. 执行操作 A
2. 检查直接结果
3. 检查间接影响（其他组件/视图）
4. 撤销操作，恢复原状态

**验证点**:
- [ ] 操作 A 直接结果正确
- [ ] 受影响的组件 B 更新
- [ ] 受影响的组件 C 更新
- [ ] 撤销后所有组件恢复

### 测试 3：数据流完整性

**目标**: 验证数据在各个环节正确流转

```
数据流检查点：
    │
    ├── UI 输入 → 表单验证
    ├── 表单验证 → API 请求
    ├── API 请求 → 后端处理
    ├── 后端处理 → 数据库存储
    ├── 数据库存储 → API 响应
    ├── API 响应 → 前端状态更新
    └── 前端状态更新 → UI 渲染
```

**验证点**:
- [ ] 每个环节数据格式正确
- [ ] 错误处理正确
- [ ] 状态转换正确

## 多视图联动对照表

### 示例模板

| 功能 | 视图 A 函数 | 视图 B 函数 | 联动点 |
|------|------------|------------|--------|
| 显示列表 | `renderListA()` | `renderListB()` | 同一数据源 |
| 显示详情 | `showDetailA()` | `showDetailB()` | 同一 ID |
| 状态显示 | `updateStatusA()` | `updateStatusB()` | 同一状态变量 |
| 操作反馈 | `showToastA()` | `showToastB()` | 同一通知机制 |

## 回归测试清单

每次修改 UI 或逻辑后，执行以下测试：

### A. 状态一致性

- [ ] 视图 A 显示状态 X → 视图 B 也显示 X
- [ ] 视图 A 修改 X → 视图 B 同步更新
- [ ] 刷新页面 → 状态保持

### B. 操作连锁

- [ ] 操作 A → 受影响的组件都更新
- [ ] 快速连续操作 → 无竞态条件
- [ ] 操作失败 → 错误提示 + 状态回滚

### C. 边界情况

- [ ] 空数据时 UI 显示正确
- [ ] 加载中 UI 显示正确
- [ ] 错误状态 UI 显示正确

## 测试心态

- **全覆盖** - 每个视图、每个组件都要测
- **想联动** - 改 A 时想 B、C 的影响，测 A 时也要测 B、C
- **查日志** - 看 API 返回，不要只凭 UI 判断
- **清缓存** - 优先清除浏览器缓存再测
- **测闭环** - 一个功能测试完，确认所有联动点都正常
- **记回归** - 发现问题后，记录哪些地方需要重新测试
